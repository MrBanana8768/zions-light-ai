# Compactor venv requirements (V2.0 Phase 3+ · pins audited V3.0, 2026-06-30).
#
# As of Phase 3 the compactor runs in its OWN venv (/opt/compactor-venv),
# fully separate from vLLM. That means these deps can resolve freely
# WITHOUT risk of disturbing vLLM's torch/transformers pins — the
# dependency-coupling bug class that caused the 1.9.x fire drills is now
# structurally impossible.
#
# Deliberately torch-free: fastembed uses ONNX runtime, and transformers
# is used tokenizer-only (AutoTokenizer works without a torch backend for
# fast/rust tokenizers). Keeps the compactor venv lean.
#
# Versions pinned EXACTLY for reproducible builds (V3.0). Re-audit against
# PyPI/OSV before each release and bump deliberately. transformers moved
# 4.x -> 5.x here: the last 4.x (4.57.6) carries open CVEs fixed only in
# 5.x, and we use it tokenizer-only on a known model, so 5.12.1 is both the
# clean and the correct choice — but the 4->5 major is the thing the rebuild
# boot self-test must confirm (fallback: transformers==4.57.6).

# --- proxy / API ---
fastapi==0.138.2
uvicorn[standard]==0.49.0
httpx==0.28.1
transformers==5.12.1
# REQUIRED for tokenizer.apply_chat_template — an OPTIONAL transformers dep that
# only chat templating needs, so "tokenizer-only" installs silently omit it.
# Without it main.py:296 raises, count_tokens falls to `encode(text) + 4` per
# message, and every token count in the system loses its chat-template framing
# (~22 tokens/message on Mistral). Undetectable until a long conversation
# overflows the context window: observed 2026-08-27 as repeated vLLM 400s on a
# ~200-message conversation with a ~5,250-token undercount. See REMEDIATION.md.
# NOT SUFFICIENT ALONE — the served model must also carry a chat_template.
jinja2==3.1.6

# --- V2.0 Phase 3: episodic memory ---
# chromadb runs EMBEDDED (in-process, sqlite-backed) — we do NOT run the
# Chroma HTTP server, so CVE-2026-45829 (pre-auth code injection via the
# server's /api/v2 collections endpoint with trust_remote_code) is not
# exposed. Affects all 1.x with no fix yet; bump to the patched release once
# published. Recorded as known/accepted in CHANGELOG [3.0].
chromadb==1.5.9
fastembed==0.8.0           # BAAI/bge-small-en-v1.5 embeddings via ONNX (no torch)

# --- v3.1.1: an ACCURATE local token count (compactor/tokens.py) ---
# The tokenizer vLLM itself uses. Before this, a /tokenize outage dropped the
# budget straight to a transformers-converted tekken vocabulary that reads
# 23-51% low on this model's assistant content -- which is what took compaction
# down on 2026-08-29 and cost the user 80+ turns of context per message.
#
# Measured cost on the v3.0.5 image: +82 MB to this venv (382 -> 464 MB, ~0.4%
# of the 20 GB image), 0.59s import, +70 MB RSS, NO torch. It pulls pycountry
# (23 MB of ISO tables, incidental) and tiktoken, and it moves numpy
# 2.5.1 -> 2.3.5 -- verified that chromadb 1.5.9 and fastembed still import
# cleanly on that version before pinning it here.
#
# PINNED, and note the hazard: vLLM declares mistral_common[image]>=1.10.0 with
# NO upper bound, so its resolved version drifts independently of this pin and
# nothing enforces agreement. That is why tokens.check_divergence exists --
# a local tokenizer that silently disagrees with the enforcing server is the
# 2026-08-28 bug wearing a better disguise. Bump this deliberately, and check
# what vLLM resolved when you do.
mistral_common==1.11.7
