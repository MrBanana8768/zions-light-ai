# Incident 2026-08-28 — context collapse, and a hotfix that would not boot

**Status:** resolved in production by hotfix; permanent fix on `fix/v3.1-remediation`.
**Severity:** S1 — the assistant answered from 4 messages of a 65-message
conversation, for days, while every layer reported success.
**Scope:** two problems, both after [INCIDENT_2026-08-24.md](INCIDENT_2026-08-24.md)
closed. Problem A is the outage (two separate down events, one cause).
Problem B is the failed hotfix deployment that followed it.

**Timestamp convention.** UTC throughout, matching the log bundles
(`logbundle-20260828T015755Z`, `logbundle-20260828T044020Z`) and the naming of
the previous incident file. Local time is MST; the whole of this incident falls
on the evening of **2026-08-27 MST**.

**Privacy.** Conversation identifiers are redacted as in `REMEDIATION.md`. No
conversation content is quoted. Character counts and token counts are structural
measurements, not content.

---

## The one-paragraph version

The compactor's token counter was reading **23% low on a real payload and 34–51%
low on assistant content specifically**. Nothing in the system could detect this,
because every component that might have caught it was consulting the same wrong
oracle. The undercount made the summarizer build batches it believed were under
budget and were not; vLLM rejected them with 400; compaction fell back to
forwarding the original messages; the full conversation then arrived at the hard
budget guard, which shed 60 of 65 turns to fit and returned HTTP 200 with a
fluent reply. The user's report was not "an error occurred." It was that the
assistant had forgotten who she was.

The undercount's dominant term was not framing overhead. It was **vocabulary
mismatch on characters the model itself likes to emit** — long horizontal rules
drawn from U+2501 and U+2500. One reply held 1,710 of one and 441 of the other:
roughly **4,275 tokens, 13% of the 32,768-token window, spent on decoration**,
priced by the local tokenizer at a small fraction of what the server charged.

# Problem A — context collapse

## A.1 What the user experienced

The assistant stopped remembering things it had been told minutes earlier. It did
not error. It did not warn. It produced coherent, in-character, fluent replies
built on almost none of the conversation. Twice the pod went down hard enough to
notice; between those events it was degrading continuously and invisibly.

This is the second time in one week that the failure presented as *"she forgot
me"* rather than as an error. That is the single most important fact in this
document, and §A.7 returns to it.

## A.2 The cascade

Five stages. Each one is individually reasonable; the composition is not.

**1 — The counter under-reads.**
`count_tokens` estimates locally with a `tekken.json` vocabulary converted by
transformers. vLLM prices the same text through `mistral_common`. The two
disagree, and they disagree *most* on exactly the content the model produces.
Measured on the live payload:

```
payload: local=122106  vLLM=150050  scale=1.23x
```

Per message type the error is neither uniform nor even the same sign:

| Content | Local vs. vLLM |
|---|---|
| System | reads high |
| User | reads ~9% high |
| **Assistant** | **reads 34–51% low** |

A single decorative rule, measured alone: `local=15  vLLM=809  scale=53.93x`.

**2 — The summarizer packs over-budget batches.**
`_chunk_to_budget` filled batches to a 29,696-token budget using the local count.
Reconstructed against the real conversation:

```
budget=29696   older turns=61   measured scale=1.19x
  OLD (scale 1.0)   4 batches, largest=36280  -> OVERFLOWS -> 400
```

**3 — vLLM rejects with 400.** Correctly. The batch genuinely did not fit.

**4 — Compaction degrades to a pass-through.** On summarization failure the
compactor forwards the original messages rather than a summary. Reasonable as a
fallback in isolation; here it means the *entire* conversation proceeds to the
next stage on every single request.

**5 — The hard budget guard sheds, and reports success.**
`_enforce_hard_budget` dropped oldest turns until the payload fit:

```
reserve  limit    kept  exact_tokens  fits?
16384    16384    4     15155         YES
```

**4 messages of 65.** HTTP 200. A WARNING line in a log nobody was watching,
phrased as a normal operation. The model answered from what it was given, which
is all it can ever do.

## A.3 Root cause

**A component budgeted against a limit it did not measure.**

Not "the tokenizer was wrong" — tokenizers disagree all the time and that is
survivable. The defect is that the compactor made irreversible decisions about
what the user would be allowed to say to the model, using an estimate of a
quantity the enforcing server would compute exactly, on request, over localhost,
in single-digit milliseconds. `/tokenize` was running the entire time.

Three properties made it undetectable:

1. **Shared oracle.** The guard, the compaction trigger, and the summarizer all
   called `count_tokens`. A disagreement between them would have been a signal.
   Agreement between them was worth nothing — and agreement is what monitoring
   saw.
2. **The error tracked content the model generates.** Long assistant replies with
   heavy decoration were the worst case, so the failure got worse the longer a
   conversation went — indistinguishable, from outside, from "long conversations
   are hard."
3. **Degradation was fluent.** Every downstream layer had a graceful fallback.
   Composed, the graceful fallbacks produced a system that lied.

## A.4 Contributing cause — a correction to REMEDIATION P0-0

`REMEDIATION.md` P0-0 (F60) diagnosed the counter three days earlier and
attributed the error to missing chat-template framing: *"roughly 22 tokens per
message… the error scales with message count, not content length."*

**That is now known to be the minor term.** The framing gap is real and the
`jinja2` fix stands, but it cannot produce a 1.23x payload-level error and it
cannot produce a 53x error on a single message. The dominant term is vocabulary
mismatch on content. P0-0's stated scaling law is backwards for the case that
actually took production down, and an implementer optimising for message count
would have missed this entirely. **P0-0 has been corrected in place.**

This is worth naming as its own finding: a partially-correct root cause, written
down confidently, cost time during the live outage.

## A.5 Why diagnosis took hours

Six hypotheses were raised and killed before the cause was found: the prescreen
pass, injected memory, the retrieval block, tool schemas, image parts, and
post-guard merges. Each was plausible, each was consistent with the logs, and
each was wrong.

What broke the deadlock was not a better hypothesis. It was **reproducing the
payload offline and asking the server what it weighed** — replacing inference
about the system with a measurement of it. Every hour before that was spent
reasoning from numbers that were themselves the defect.

The lesson is not "think harder." It is that **a diagnosis which consumes the
suspect component's output cannot clear that component.** When the counter is
under suspicion, no log line derived from the counter is evidence.

## A.6 The fix

`count_tokens_exact(messages)` asks vLLM's `/tokenize` for the number vLLM will
actually charge, with a short timeout and a once-per-process warning on failure.
It returns `None` rather than raising, and every call site falls back to the
local estimate — the compactor must not lose the ability to serve because a
side channel is slow.

Three call sites use it:

- **The guard** measures the real payload and derives a `scale` factor, applied
  to per-message estimates so shedding arithmetic is proportionate.
- **The verify step** re-measures the shed result exactly rather than trusting
  the scaled estimate.
- **The summarizer** measures before batching, so `_chunk_to_budget` packs
  against real numbers.

Verified against the live conversation:

```
guard:       150050 -> 15155  (limit 16384)  FITS
summarizer:  NEW (measured)  5 batches, largest=29909  FITS
             OLD (scale 1.0) 4 batches, largest=36280  OVERFLOWS -> 400
```

**The summarizer half is the decisive one.** The guard was the visible symptom,
but the guard only ever ran on the full conversation because summarization was
failing. Fixing batching removes the cascade at its head.

### A.6.1 A correction recorded because it nearly shipped

On the strength of the table in §A.2, I advised dropping `GENERATION_RESERVE`
from 16,384 to 2,048 — more headroom, more turns retained, obviously good.

**Wrong.** That table measures *input*. The reserve exists for *output*, and this
user's assistant replies measure **7,513–11,347 tokens**. A 2,048-token reserve
would have truncated nearly every reply mid-sentence, trading a context bug for a
worse one. Keep 16,384, or 12,288 if headroom is needed.

The general form: **a headroom parameter cannot be tuned from a table that does
not contain the thing it reserves for.**

## A.7 What this was not

Recorded to stop these coming back:

- **Not the memory store.** Facts, episodic, and summaries were intact throughout
  — 105 facts, 98 episodic documents, L1=5, verified during the migration. Memory
  was never the problem in either incident this week.
- **Not the 2026-08-24 chain corruption.** That was client-side and separately
  fixed. This incident never touched message structure.
- **Not images.** `COMPACTOR_MAX_RETAINED_IMAGES=0`; no image parts in the payload.
- **Not tools.** Measured: 0 tools, 0 functions registered.
- **Not the user's fault**, and worth saying plainly: the decorative characters
  came from the model, under a system prompt that did not forbid them. The prompt
  has since been updated, which reduces exposure but is **not the fix** — the
  counter must be right regardless of what the model chooses to emit.

# Problem B — the hotfix would not boot

## B.1 What happened

With production degraded, the owner elected to hot-patch the running pod rather
than wait for a tagged build — a deliberate, stated relaxation of the standing
"production runs tagged images" rule for the duration of the outage.

The patch failed on start:

```
ImportError: cannot import name 'StoreUnreadable' from 'memory'
```

The owner rolled back. Production stayed degraded longer than it needed to.

## B.2 Root cause

I supplied `main.py` from `fix/v3.1-remediation`. That file depends on
`StoreUnreadable`, a symbol that exists only in the branch's `memory.py`.
Production was running v3.0.5. **A single file was lifted out of a branch and
dropped onto a different commit, and its dependencies did not come with it.**

The correct construction — used on the retry — is to build the patch from the
**deployed tag** in a worktree, changing only what the fix requires.

A second, smaller failure followed: `spec_from_file_location` returned `None`
because the staged file was named `main.py.new`, and `.new` is not an importable
extension. Renaming to `.py` resolved it.

## B.3 Why this is a finding and not just a bad night

The same class of error recurred **five times** across this week's work: a symbol
referenced in one module that is not imported, or not present, in the module it
lands in — `memory.StoreUnreadable`, `assert_in`, an unimported `StoreUnreadable`
in `commands.py`, and two variants besides. Every one of them would have been
caught by importing the module once.

No gate does this. `selftest.py` runs *inside* an already-working process, so it
cannot catch a module that fails to import at all. The missing check is trivial
and belongs in CI and in the pre-deploy path:

```bash
python -c "import compactor.main, compactor.memory, compactor.commands"
```

**A patch built from a branch must be verified against the commit it will land
on, not the commit it was written on.** That is the process finding, and it is
worth more than the individual bugs.

# Cross-cutting findings

**C1 — Fluent degradation is worse than failure.** Every fallback in this cascade
was individually well-intentioned. Composed, they converted a hard, loud,
immediately-diagnosable 400 into a soft, quiet, week-long lie. A fallback that
cannot signal that it fired is not a fallback; it is a cover-up.

**C2 — The user is the monitoring.** Both incidents this week were detected by a
human noticing that a companion had changed. No alert fired. No dashboard moved.
`COMPACTOR_ALERT_WEBHOOK` is still unset.

**C3 — Estimates of enforced quantities must be verified against the enforcer.**
Stated in full as a quality bar in `FRONTEND_SPEC.md` §13.

**C4 — Structural cost is invisible to everyone.** Nobody — user, operator, or
developer — could see that 13% of the context window was going to box-drawing
characters. The data existed; nothing displayed it.

**C5 — Confident, partially-correct root causes cost time.** See §A.4.

## What changed in FRONTEND_SPEC.md as a result

Four edits, all traceable to this incident:

1. **§2 obligation 7** gains the server-side reference case. The obligation
   already bound every layer; it had no example of the *server* being the layer
   that lied. Now it does.
2. **§12** — the context receipt now reports **messages the server admitted**,
   not messages the client sent. Under this incident a receipt reading "65 sent"
   would have been accurate and worthless. A new `context_shed` notice separates
   *discarded* from *compressed*, and per-message token cost is specified.
3. **§15** — the received-context echo is extended from a triple to
   received / admitted / exact tokens / headroom, sourced from `/tokenize`.
   Per-message cost added as recommended.
4. **§13** — new **budget-verification** quality bar, and the context-fidelity
   bar corrected: it now covers the client's own truncation only, because the
   receipt legitimately reports a different number than the client sent.
